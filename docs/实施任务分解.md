## 使用方式

- 任务编号 `P{阶段}-{序号}`，每个任务建议**一个提交**。
- `依赖` 列写前置任务编号；没有依赖的任务可以并行。
- 每个任务的「验收」是完成定义，必须可执行、可观察。
- 提交前缀：`feat(core):` / `feat(server):` / `feat(web):` / `feat(admin):` / `feat(storage):` / `chore(docker):` / `docs:`。

## 里程碑

| 里程碑 | 完成标志 | 预估 |
| --- | --- | --- |
| **M1** | 服务端可导入/发布题库、会员权限生效、Docker 一键起 | 6–8 人日 |
| **M2** | 客户端可下载/切换题库，进度按题库隔离，会员同步打通 | 8–10 人日 |
| **M3** | 后台可完整维护题库、兑换码、用户 | 6–8 人日 |
| **M4** | 统计、导出、部署验证、三端回归 | 3–4 人日 |

## P1 · 核心与服务端（M1）

### P1-01 · core：题目稳定 ID 与题库元数据

- **依赖**：无
- **文件**：`packages/core/src/types.ts`
- **内容**
  - `Question` 增加 `id: string`
  - `QuizData` 增加 `id: string`、`name: string`、`version: number`、`subtitle?: string`
  - 内置题库在构建期补 `id = \`${c}-${n}\``
- **验收**：`pnpm typecheck` 通过；所有构造 `Question` 的位置（含测试）都补齐 `id`

### P1-02 · core：`qkey()` 切换到题目 ID

- **依赖**：P1-01
- **文件**：`packages/core/src/types.ts`、`logic.ts`、`achievements.ts`、`challenges.ts`
- **内容**
  - `qkey()` 返回 `q.id ?? \`${q.c}-${q.n}\``
  - 接收 `Pick<Question,'c'|'n'>` 的签名改为 `Pick<Question,'id'|'c'|'n'>`
  - 检查 `sessionPersistence.ts` 的键读写
- **验收**：`pnpm test` 通过；内置题库加 `id` 后，现有 localStorage 键不变

### P1-03 · core：`validateBank()`

- **依赖**：P1-01
- **文件**：新增 `packages/core/src/validate.ts`，`src/index.ts` 导出
- **内容**：按设计文档 5.3 实现，返回 `{ ok, errors, warnings, removed }`
- **验收**：单测覆盖题库 ID 非法、题目 ID 重复、`a` 越界、章节缺失、`o` 长度错误

### P1-04 · core：单测补齐

- **依赖**：P1-01、P1-02、P1-03
- **文件**：`packages/core/test/core.test.ts`
- **验收**：`pnpm test` 全绿；新增 ID 兼容、`validateBank`、键不变三类用例

### P1-05 · server：数据库 schema 与迁移

- **依赖**：P1-01
- **文件**：`apps/server/src/db.ts`
- **内容**
  - `users` 增加 `role` / `member_until` / `disabled_at`
  - 新建 `banks`、`bank_chapters`、`bank_questions`、`bank_releases`、`redeem_codes`、`membership_logs`、`activity_daily`
  - `user_states` → `user_states_v2(user_id, bank_id)`，旧数据落 `builtin`
  - `user_achievements` → `user_achievements_v2(user_id, bank_id, ...)`
- **验收**：拿一份旧库启动，自动迁移且数据行数不变；二次启动不重复迁移

### P1-06 · server：内置题库幂等 seed

- **依赖**：P1-05、P1-03
- **文件**：新增 `apps/server/src/seed.ts`（复用 `questions.ts` 的加载逻辑）
- **内容**：`banks` 为空时导入 `data/questions.json`，题目 `id = ${c}-${n}`，写 `bank_releases` v1
- **验收**：空库启动后 `banks` / `bank_questions` / `bank_releases` 有数据；已有数据时不覆盖

### P1-07 · server：题库服务（导入 / 发布 / 查询）

- **依赖**：P1-05、P1-03
- **文件**：新增 `apps/server/src/banks.ts`
- **内容**
  - `importBank(json, operatorId)`：校验后写草稿
  - `publishBank(id, note, operatorId)`：序列化 bundle，`current_version + 1`
  - `getPublishedBank(id, version?)`、`listPublishedBanks()`
- **验收**：导入两份不同题库互不影响；发布两次得到 v1/v2，旧版本仍可读

### P1-08 · server：公开题库 API

- **依赖**：P1-07
- **文件**：`apps/server/src/routes.ts`
- **内容**
  - `GET /api/banks`：已发布元数据
  - `GET /api/banks/:id/bundle?version=N`：完整包，ETag / 304 / gzip；`builtin` 公开
- **验收**：curl 能拿到 2726 题的包；重复请求返回 304

### P1-09 · server：会员、兑换码与 `requireMember`

- **依赖**：P1-05
- **文件**：新增 `apps/server/src/membership.ts`，修改 `routes.ts`
- **内容**
  - `requireMember` 中间件
  - `POST /api/auth/register` 写 7 天试用 + `membership_logs(action='trial')`
  - `GET /api/membership`、`POST /api/membership/redeem`

- **验收**：免费用户访问需会员接口返回 403；兑换后返回 `expiresAt`；同一码第二次兑换失败；续期正确叠加

### P1-10 · server：按题库同步

- **依赖**：P1-05、P1-09
- **文件**：`routes.ts`、`db.ts`
- **内容**：`GET/PUT /api/banks/:id/sync`，保留 `mergeStates` 与成就复核
- **验收**：两个题库分别 PUT，互不覆盖；`builtin` 的旧数据可读；免费用户 403

### P1-11 · server：角色与禁用

- **依赖**：P1-05
- **文件**：`auth.ts`、`db.ts`、`routes.ts`

## 可并行的工作

- `P1-03 validateBank` 与 `P1-05 schema` 可同时进行。
- `P1-09 会员` 与 `P1-07 题库服务` 可同时进行。
- `P1-12 admin 骨架` 可与整条服务端链路并行。
- P3 的兑换码、用户管理可在题库编辑完成前并行。

## 建议先做的验证（Spike）

| 验证 | 时点 | 目的 |
| --- | --- | --- |
| `file://` 下 IndexedDB 可用性 | P2-01 前 | 决定回退策略是否需要更严的体积限制 |
| `node:sqlite` 在 Docker 卷上的 WAL 行为 | P1-05 后 | 确认备份方式（需带 `-wal` / `-shm`） |
| 2 MB 题库包的 vdom 解析耗时 | P2-10 后 | 决定是否需要 Web Worker 解析 |

## 风险提示

- `P1-02` 改动面最大，所有 `qkey` 调用点必须一次改完，靠 `typecheck` + 单测兜住。
- `P2-03` 迁移必须幂等，否则重复启动会覆盖新数据。
- `P1-06` seed 必须只在空库执行，Docker 重建不能覆盖后台发布内容。
- `P3-04` 编辑题目时永远不能改题目 `id`，只允许改 `c` / `n` / 内容。
