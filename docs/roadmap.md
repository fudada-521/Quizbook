## 二、真实缺口（按优先级）

### 1. 数据可靠 —— 有实际丢数据的路径

这是三块里**唯一会造成数据丢失**的问题，应先于一切新功能。

- **推送竞态会吞掉答题记录**（`apps/web/src/store/QuizStore.tsx:432-470`、`:396-430`）
  `pushSnapshot()` 在请求返回后无条件 `setPersisted(pushed.state)`。如果请求期间用户又答了几题，这几题会被服务端返回的旧快照覆盖；同时 `lastPushedRef` 被更新，防抖逻辑认为「已同步」不再重推，本地存储随后也被旧状态覆盖。
  窗口 = 一次网络往返（弱网下可达数秒）。
- **离线后不会自愈**：没有监听 `online` / `visibilitychange`，同步失败后只能等用户再次作答或手动点同步。
- **409 冲突被当成普通离线**：`CloudClient.push` 在 409 时抛 `ApiError`，但响应里其实带着服务端合并结果，客户端直接丢弃了。
- **桌面/移动仍依赖 WebView localStorage**：没有可备份的实体文件，清缓存/换机即丢（目前只能靠手动导出）。
- 会话快照在答题期间随每秒计时 tick 重写 localStorage（`QuizStore.tsx:316-324`），挑战模式下写入偏频繁，属小问题。

### 2. 内容质量 —— 已有明确清单，只差执行

用脚本实测了 `data/questions.json`：

| 问题 | 数量 |
|---|---|
| 题干依赖图片/表格（含「图 / 如下表 / 下表」等） | 83 |
| 选项长度 < 2 字（疑似 OCR 截断） | 31 |
| 解析为空 | 4 |
| 题号重复 | 0 ✅ |

分布均匀（每章 23–200 题），没有结构性问题，属于可逐条修完的量级。

### 3. 做题体验 —— 缺的是「复习闭环」，不是细节

现有体验已经打磨得不错（Refract 主题、可访问性审计已修、音效触觉反馈）。真正缺的是：

- **没有到期复习**：目前只有顺序/随机/错题重练，没有基于遗忘曲线的「今天该复习哪 20 题」。这是刷题工具最大的价值增量。
- 学习统计只有首页概览，没有近 30 天正确率趋势和章节薄弱项。
- 移动端没有专门打磨（PWA 安装引导、返回键、底部安全区）。
- 挑战模式的错题与普通错题本的互通关系没有明确规则。

## 三、关键取舍（建议先拍板）

**建议：主端定为「手机 PWA + 网页」，桌面/移动原生壳只保持能跑，不做上架。**

理由：

- 小范围分享时，发一个链接是最低成本；PWA 可以「添加到主屏」，体验接近原生。
- 一套代码、更新即时，不用管签名、审核、APK 分发和版本兼容。
- 一旦定了主端，TODO 里「iOS/Android 上架」「macOS 签名」「原生存储适配层重写」可以整体砍掉，省下大量工时。

**次要取舍：数据安全优先于内容与体验。** 先花 1 天堵住丢数据的路径，再谈新功能；否则新功能做得越多，丢得越多。

## 四、路线图

### Now · 本周（约 1 天）：做到「不会丢数据」

| # | 任务 | 验收标准 |
|---|---|---|
| 1 | 修推送竞态：请求返回后不要整体覆盖，改为合并/仅应用无本地变更的情况；或给每次变更打序号，落后则丢弃响应 | 人为加 500ms 网络延迟，连续快速答题 20 题，刷新后 20 题全在 |
| 2 | 失败自愈：监听 `online` 与 `visibilitychange(visible)`，触发 `syncNow()`，最多退避重试 3 次 | 断网答题 → 恢复网络 5 秒内状态回到 `synced` |
| 3 | 409 冲突处理：使用响应体里的 `state/version` 重新合并并重推 | 两端同时推送不再进入 `offline` |
| 4 | 自动备份：同步成功后把快照写入 IndexedDB，保留最近 7 份，设置页可下载 | 「设置 → 账号与同步」可见备份列表并能下载导入 |
| 5 | 真正部署一次：`docker compose up -d --build` + HTTPS + GitHub OAuth 回调 | 手机 4G 下完成设备码登录与同步 |

> 第 5 项是「小范围分享」的前置条件；如果暂时只有自己在用，可以只做本机/局域网。

### Next · 2–3 周：内容可信

| # | 任务 | 验收标准 |
|---|---|---|
| 1 | 写 `scripts/audit-questions.mjs`，输出图表题 / 短选项 / 空解析 / 重复题干 / 异常长度报告到 `docs/question-audit.md` | 一条命令生成报告，数量与本次实测一致（83 / 31 / 4 / 0） |
| 2 | 逐条修 83 道图表题：优先补文字描述；确需配图的题目**先标记、不急着改题库结构** | 报告中图表题数量降为 0 或均有「已确认可忽略」备注 |
| 3 | 修 31 处短选项与 4 处空解析 | 同上 |
| 4 | 把质检脚本挂到 `pnpm check`，以后改题库自动报警 | 引入一条坏题后命令退出码非 0 |

> 不建议给题库加 `image` 字段：会牵动 core 类型、schema、三端资源和离线单文件构建，收益小于成本。文字描述能覆盖绝大多数。

### Later · 1–2 个月：复习闭环

| # | 任务 | 说明 / 验收 |
|---|---|---|
| 1 | 到期复习 | 用已有 `answers[key].t` 与 `wrong[key]` 计算待复习队列（简化间隔：错≤1 天、对 1 周、连对 2 次 1 月），首页加入口。**不改 schema**。验收：连续用一周后队列非空且题量合理 |
| 2 | 学习统计页 | 近 30 天正确率曲线、章节薄弱 Top 5、挑战成绩趋势 |
| 3 | 移动端打磨 | PWA 安装引导、Android 返回键、底部安全区 |
| 4 | 明确挑战错题规则 | 挑战中的错题是否进错题本：建议「模拟考进、限时挑战不进」，写进 README |

### 贯穿：最低成本的工程护栏

不做 ESLint / pre-commit 大工程，只加两道保险：

- `pnpm check` = `pnpm typecheck && pnpm test && node scripts/audit-questions.mjs`
- （可选）GitHub Actions 只跑 `check` + `build`，约 30 行 YAML。**如果只做一件事，就做这个**——它能防止「改体验时改坏 core」。
- 顺手同步文档：`CLAUDE.md` 的 schema v5、66 条单测；`README` 的已知限制。

## 五、不做清单（明确放弃，避免反复纠结）

- App Store / Google Play 上架、代码签名、原生存储适配层重写
- 增量同步、快照压缩（当前数据量下收益极低）
- 多用户/社交/排行榜/付费
- CSS 大重构（3023 行确实多，但可以等改动频繁时再按视图拆分，不做一次性重写）
- 题库结构大改（如加图片字段、重排题号）
